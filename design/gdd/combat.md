## Summary

本系统定义一场可运行、可打包并可交给外部全流程测试的 2D 战斗切片。产品文档确认角色牌组公式、反应目标和胜利条件清单；Unity 原型提供卡牌数值和少量配方的兼容证据。为了让迁移可以直接开工，本文把单场夹具所需的回合、抽牌、AI、配方覆盖、被动归属和胜负优先级登记为 `MIGRATION-TEMP (autonomous)`。这些是可替换的迁移决定，不冒充正式产品规则；完整角色阵容和后续平衡仍需专项设计。

> **Quick reference**: Layer: Core + Feature | Priority: MVP | Key deps: Card Catalog & Deck, Opponent Rules, Battle UX

## Overview

### 目标

为 Godot 4.6.2 的 PC 原型提供一份可实现、可测试的战斗规则边界。规则应从卡牌数据和战斗状态中计算结果，不依赖 Unity UI、Prefab、TextMeshPro 或 Addressables。Godot UI 负责呈现状态并提交玩家命令，不拥有战斗规则。

### 设计状态标签

本文每个事实按下列状态标注：

- **设计已确认**：用户会话确认的项目设置，或产品文档明确写出的目标规则。文档的歧义部分仍标作待定。
- **原型实际行为**：Unity 源码当前的可执行行为；仅作为迁移证据，不自动升级为正式玩法。
- **迁移期暂定**：为可回退的单场切片提出的临时路径，使用前应在迁移任务中再次显式登记。
- **尚待设计**：现有材料无法给出唯一实现；不允许由实现者自行选择后伪装成既定规则。

本文另以 **`MIGRATION-TEMP (autonomous)`** 标识为完整可玩/可打包单场切片作出的暂定决定。这些决定是本轮 autonomous 流程记录的推荐默认值，足以驱动当前切片实现；它们不改写产品设计，负责人可在审阅时替换。凡是产品文档尚未定案的事项，在正式发布或扩展完整阵容前仍需重新确认。

产品规则依据为仓库外一层的 [TCA-Godot版.md](../../../TCA-Godot版.md)；当前可执行行为依据 [BattlePrototypeRules.cs](../../Assets/Scripts/TCA/Battle/BattlePrototypeRules.cs)、[BattlePrototypeState.cs](../../Assets/Scripts/TCA/Battle/BattlePrototypeState.cs)、[TcaModels.cs](../../Assets/Scripts/TCA/Data/TcaModels.cs) 和[规则对照矩阵](../../docs/migration/rule-parity-matrix.md)。

### 范围边界

**本 GDD 覆盖**：战斗初始化接口、卡牌类型与实例、抽牌接口、出牌合法性、能量、回合、两牌反应、角色效果接入点、胜负评估、战斗 HUD 所需状态，以及一场 PC 战斗切片的验收标准。

**本 GDD 不定义**：冒险地图、剧情、局外成长、完整角色养成、经济、在线多人、有机化学内容、AI 难度曲线、美术风格规范或完整 UX 视觉规格。切片内的固定策略 AI 仅服务于确定性外部测试，不代表正式敌人设计。

### 单场切片 autonomous 默认值

为让切片当前可进入实现和外部全流程测试，本 GDD 暂定如下完整规则集。每项都在决策日志中记录了来源与影响；它们只服务一个可回退的战斗夹具。

| ID | `MIGRATION-TEMP (autonomous)` 决定 | 选择理由与影响 |
|---|---|---|
| MT-01 | 单场 1v1：玩家控制一方，对手由确定性规则 AI 控制；不做角色选择/冒险入口。双方使用 Unity 当前 `CreatePrototypeHand` 的 10 张手牌、30 HP、8/8 能量。 | 复用现有可运行原型数据，聚焦迁移和完整一场战斗；不代表最终队伍人数、角色 HP 或牌组 UI。 |
| MT-02 | 双方各有 12 张有限抽牌堆，ID 与 Unity 随机池一致，每个 ID 各一张；使用 fixture seed `0x54434101` 打乱。开局各 10 张手牌，此后每个己方回合开始抽 1 张（首次不额外抽），手牌无上限，不洗回弃牌堆。 | 固定初始牌组是完整 1v1 夹具的一部分；牌库耗尽后抽牌无效果。空手牌立即失败，即使抽牌堆或弃牌堆仍有牌。这是对“失去所有手牌”的可执行临时解释。 |
| MT-03 | 玩家先行；玩家结束回合后进入 AI 回合，AI 最多执行一个动作后结束，再回到玩家。后续己方回合开始时先恢复 2 能量（上限 8）再抽 1；玩家可主动结束或在无合法动作时自动结束。 | +2/8 来自 Unity 原型；交替顺序、AI 一动作和回合开始抽牌是为单场流程确定的临时规则。 |
| MT-04 | 保留原型卡费、伤害及反应费；C/B/S/Ar 按原型效果，N 按文字暂实现为“下次受伤 -1”，若到对手下一次回合结束仍未触发则移除。O 首次伤害 +1 与每方每回合首个成功反应抽 1 仅属于 `prototype_fixture` 的双方对称全局兼容修正，不标为角色被动；C 折扣在本方回合结束时过期；B 待抽标记跨回合保留至成功反应。 | 兼容原型可见行为，修正 C 折扣意外跨回合；给 N 卡补上文本效果。所有 fixture 修正都与正式角色被动隔离。 |
| MT-05 | 切片配方：C+O→CO/CO₂，N+O→NO/NO₂，Cl+Cl→Cl₂，C+C→C，N+N→N₂，O+O→O₂。多产物须玩家选；AI 选稳定 ID 顺序的第一项。新增 CO₂/NO/N₂/O₂ 数值为临时游戏效果；未列配方均无效。 | 覆盖 Unity 当前六个预览组合，修复三种“成功却没有产物”的执行缺口。公式是物质标识，配方解释和战斗值均不是化学事实。 |
| MT-06 | 已打出牌和反应输入进入弃牌；生成的反应产物作为新卡实例加入手牌。AI 每回合优先可支付的有效反应，再选基础伤害最高的合法伤害牌，然后选费用最低的合法自用牌；并列时按实例定义 ID、再按实例 ID 排序。选到动作后只执行一项；没有动作就结束。 | 无随机决策，动作完全可复现。若反应候选需要选产物，AI 用 MT-05 次序规则。 |
| MT-07 | 一方 HP≤0 或当前手牌为 0 即失败；对方胜利（OR 解释）。每个原子动作后检查终局；若同次原子结算双方均满足失败条件则平局。 | 对称规则闭合双方战斗；将文档并列胜利条件解释为 OR。该语义仍是临时的，不改变产品原文。 |
| MT-08 | 缺牌、无效配方、非法目标、能量不足、未选或取消多产物反应均完全不改状态；已放入的卡留在槽位。玩家可清槽退回手牌；回合结束时未完成的槽牌自动退回手牌。 | 原子失败避免损牌/费用，槽牌回收避免软锁。 |
| MT-09 | 正式被动归属角色实例，仅角色参战时触发。此单场 fixture 不创建角色、不启用角色被动；Unity 的首伤 +1 与首反应抽牌只作为双方对称、显式标记的 `prototype_fixture` 全局修正，不归属 C/O。 | 分开角色设计与 Unity 原型全局钩子，避免把源实现缺陷当正式规则；fixture 仍覆盖已有结算效果。 |
| MT-10 | 键鼠关键流程采用混合操作路径；支持鼠标操作和键盘焦点/快捷键，拖放不是唯一入口。暂用 `Tab/Shift+Tab`、方向键、`Enter/Space`、`R/C/E/Escape` 映射，允许后续 UX 调整。 | 满足已确认的 PC 键鼠主输入要求；不要求纯键盘完成整场，也不要求每项操作都重复提供两种设备入口。 |

科学事实和卡牌游戏抽象分开记录：`CO₂`、`NO₂` 等公式字符串表达物质身份；上述“各投一张元素牌即可生成候选物质”是游戏规则，不表示反应方程式原子守恒。配方需另有科学来源/审核字段；费用、伤害、抽牌或控制效果是独立的游戏化效果，不可从化学公式推断。

| 化学范围 | 设计已确认（产品文档） | 产品文字以元素和化学反应为基础，限定主族且排除第四周期。 | 六组切片配方按 MT-05 的显式数据表运行；每条配方另存内容来源/审核状态。 | 14 名角色完整配方全集及科学审核资料。 |

| 初始能量 | 设计已确认（产品文档） | 初始值等于上阵角色 `energy` 总和。 | 切片 fixture 使用固定 8/8 能量，不调用角色选择初始化。 | roster 中角色能量数值、阵容上限及最大能量规则。 |
| 胜负 | 设计已确认（条件清单）＋迁移期暂定 | 产品列出敌方 HP=0、敌方手牌清空；未说明逻辑关系。 | MT-07 以任一条件（OR）判败，对称应用于玩家；同一原子结算双方同时失败为平局。 | OR/AND 是否为正式规则、多人目标与完整剧情战斗的特殊胜利条件。 |

| 对手行动 | 原型未实现＋迁移期暂定 | Unity 只呈现敌方 HP/手牌数字，没有敌方牌组、出牌或回合。 | MT-06 的确定性每回合一动作 AI，满足完整攻防循环和复现需要。 | 正式 AI、难度策略、敌方牌组构筑和行为表现。 |

### 2. 数据模型与数据边界

以下字段是规则系统需要的逻辑概念，不要求与 Godot Resource、JSON 或场景节点一一对应。序列化方案由后续架构决定。

| 数据对象 | 逻辑字段 | 校验与边界 | 状态 |
|---|---|---|---|
| `CardDefinition` | 唯一 `id`、显示名、元素/物质标识、内部类别、费用、规则效果（类型+参数）、目标类型、元素牌标志、艺术资源引用 | ID 非空且唯一；费用/伤害非负；元素反应只接受元素牌；切片仅允许本 GDD 列出的效果类型，未知效果 ID 阻止开局。规则文案不能替代效果数据。 | Unity 已有近似字段；切片效果类型/参数由卡表和 MT-04 定义。完整产品再扩展 schema。 |
| `CardInstance` | 唯一实例 ID、定义 ID、所有者、当前区域、临时修正 | 同一实例同一时间只属于一个区域；同定义牌可有多个不同实例。禁止把目录里的单个定义对象直接当作整副牌中唯一物理牌。 | Godot 迁移建议；Unity 目前用共享定义对象表示手牌条目。 |
| `CharacterDefinition` | 元素 ID、显示名、HP、能量、被动定义、招牌牌 ID、牌组列表 | 牌组中每个定义 ID 必须存在；每位角色目标 10 个条目，重复项作为牌组数量。 | 产品公式已确认；角色数值/效果未全部确认。 |
| `BattleState` | 参与方、HP、当前/最大能量、轮次与阶段、手牌/抽牌堆/弃牌堆、反应槽、临时效果、终局状态 | 切片 HP 不低于 0；能量在 0–8；卡牌实例只处于一个区域；终局状态只可从 ongoing 进入一次。 | Fixture 数值/终局由 MT-01–08 定义；正式上限随完整阵容设计。 |
| `ReactionRecipe` | 规范化后的两个输入元素 ID、允许的产品 ID 列表、适用条件/消耗 | 输入顺序不影响结果；每条记录有唯一键；每个产品 ID 指向卡牌定义；多结果通过明确选择返回。 | 产品行为已确认；配方表结构为实现建议；内容项尚待设计。 |
| `BattleActionResult` | 成功/失败、状态是否变化、反馈事件/信息 | 失败动作不得局部扣费、移卡或消费状态；界面不能只凭文字判断规则结果。 | Unity 已有成功标志和日志字符串；结构化事件是迁移建议。 |

**所有权边界**：`BattleRules` 接收命令并验证状态，返回状态变更/事件；`BattleState` 存储战斗数据；`CardDefinition` 与 `ReactionRecipe` 是内容数据；UI 仅负责输入映射、可操作状态和反馈。不要把 `CardView`、场景节点或面板文本变成规则来源。

**数据来源边界**：Unity 的 `CreateCardCatalog` 有 12 个卡牌定义，`CreateCharacters` 只有 C/N/O/Cl 四个数据对象，14 人表是设计资料而非可执行定义。Godot 首批内容应在数据表中标清 `prototype`、`approved` 或 `draft`；未确认的卡牌规则不能通过文案字段偷偷生效。

### 3. 战斗准备与牌组

**设计已确认（产品文档）**：每名上阵角色提供 10 张牌，最多选择 4 名角色；起始能量为角色 `energy` 的总和。若选择 N 名角色，角色贡献条目数为 `10 × N`，其中 `N ≤ 4`。产品文档没有据此规定牌堆、起手或回合抽牌数。

**原型实际行为**：Unity 开局固定手牌为 `c,n,o,cl,b,s,ar,co,no2,h2o2` 共 10 张；之后从 12 个定义 ID（`c,n,o,cl,b,f,s,ar,co,no2,h2o2,cl2`）等概率抽取并允许无限重复；`f` 和 `cl2` 不在起始手牌。固定手牌不是从抽牌池抽出。

**MIGRATION-TEMP (autonomous)**：单场双方均使用 `prototype_fixture`。固定开局手牌为上列 10 个实例；另有 12 张有限抽牌堆，每个目录 ID 各一张，按 seed `0x54434101` 分别洗牌，双方牌堆独立。开局的手牌与抽牌堆是独立装载，故相同定义 ID 可同时存在多个不同实例；手牌没有数量上限。首次部署不抽牌；其后每次一方进入自己的回合时先按 MT-03 恢复能量再抽 1 张。牌库顶部为下一张，牌库耗尽时抽牌为 no-op，不洗回弃牌堆。牌被打出或作为反应输入后进入弃牌堆；生成的产物是新实例，直接加入手牌。当前手牌为 0 会结束战斗，即使弃牌或抽牌堆仍有牌。此夹具不满足正式角色牌组公式，也不构成正式构筑/平衡结论。

### 4. 卡牌分类、出牌和结算

#### 分类

| 内部类别 | 产品文档定义 | 原型目录示例 | 玩家 UI |
|---|---|---|---|
| Damage | 直接伤害；若带 Buff 效果则应归 Buff | O、Cl、F、CO、NO₂、H₂O₂、Cl₂ | 显示实际效果，不显示 `Damage` 分类字样 |
| Buff | 为自己/对方增加增益或减益；可兼具伤害效果 | C、N、B、S | 显示实际效果，不显示 `Buff` 分类字样 |
| Solvent | 影响自己/对方手牌数量；若带 Buff 仍归溶剂 | Ar | 显示实际效果，不显示 `Solvent` 分类字样 |

Unity 的 `TcaCardPresentation` 和 `CardView` 在检查卡牌时显示内部类型，违反产品文档的显示约束；Godot 检查面板应展示卡牌名称、有效规则、费用和当前可用目标，不显示内部类别标签。

#### 出牌命令

Godot 命令包含 `card_instance_id` 与 `target_id`。切片中目标只能是 `self` 或 `opponent`，并由每张卡的数据声明；不可对已终结战斗或 HP≤0 的目标出牌。结算作为一个原子动作执行：

1. 校验阶段为当前行动方的 `player_action` 或 `ai_action`，战斗状态为 `ongoing`。
2. 校验该实例的 owner 是行动方且区域是 hand；校验目标和卡牌声明的 target kind 匹配。
3. 校验费用非负、能量足够、数据效果存在；任一失败返回有原因的拒绝结果，不写入任何状态。
4. 扣费，将所选实例从 hand 移至 discard，并按效果定义应用伤害/护盾/状态/抽牌。
5. 将能量、HP、牌区和效果事件一次性提交；完整效果和触发性抽牌结算后，评估终局。

本切片将打出的卡放入弃牌堆，不采用 Unity 当下把目录定义直接从列表移除而无弃牌区的表现。退出战斗后所有临时区域随场景销毁。

### 5. 目标合法性和反应槽

#### 目标区域

Unity 原型只有敌方目标区、玩家目标区、左右反应槽。`CardTargeting.Enemy / Self / Any` 决定出牌区域；反应槽要求 `isElementCard`。当前目录的伤害牌指向敌方；C/N/B/S/Ar 指向自身；没有 `Any` 卡。

单场切片的目标/反应定义固定如下；衍生物质按其定义行执行：

| ID | 出牌目标 | 可放入反应槽 | 说明 |
|---|---|---|---|
| `c`, `n` | 自身 | 是 | 元素输入牌；同 ID 的两个实例可合成。 |
| `o`, `cl`, `f` | 对手 | 是 | 元素输入牌。 |
| `b`, `s`, `ar` | 自身 | 否 | 只作为卡牌效果使用。 |
| `co`, `co2`, `no`, `no2`, `h2o2`, `cl2`, `n2`, `o2` | 对手 | 否 | 物质输出牌；本切片没有物质牌再参加配方的规则。 |

对已击败目标不接受伤害命令；不允许把自用卡投向对手、伤害牌投向自己，或把非元素物质牌放入槽位。当前目录没有 `Any` 目标卡；未来增加时必须单独声明其合法目标。

迁移规则建议：

- 规则层按实例所有者、手牌区域、目标类型、卡牌效果和目标状态验证，不能只靠拖放 UI 限制。
- 反应槽各最多放一个元素牌实例；相同定义的两张牌可用于同元素配方，但必须是两个不同牌实例。
- 放入槽位不扣能量；合成失败时不扣费、不消费实例、不清槽。
- 放入槽位时记录卡牌原 hand index；清槽/结束回合退回时按原 index 恢复排序。同一实例不能处于两个槽或同时存在于 hand。
- 两槽都满但配方无效时，仍允许玩家清槽/换牌；不能让无效配方导致软锁。

Unity 的规则方法虽然调用 `HandCards.Remove(card)`，却没有检查删除是否成功。因此，直接调用时可以用不在手牌中的目录定义完成“出牌/放槽”。Godot 规则层必须校验实例持有权，避免把这个调用缺口固化。

### 6. 元素反应和产物选择

#### 目标反应约束

1. 恰好两张元素牌进入合成；每个卡实例最多贡献一次。
2. 配方查表前规范化输入顺序，左右槽互换不改变候选产物。
3. 不支持的配方必须明确提示且不发生状态变更。
4. 成功时只生成一个物质；若候选列表多于一个，必须显示可选物质并等玩家确认后结算。
5. 输入卡消费、能量扣除和产品加入应原子化；失败时回滚或完全不写入。

两元素输入、同元素/异元素的产物类别和多产物由玩家选择是产品规则。单场切片配方和临时数值见 MT-05。Unicode 下标/化学式展示只影响呈现，不改变稳定 ID。科学反应事实需独立核验；当前玩法是卡牌抽象，不表示反应方程式已配平或符合原子守恒。

#### 当前 Unity 配方（兼容证据）

| 输入 ID（无序） | Unity 预览/执行行为 | 单场切片行为（MT-05） | 备注 |
|---|---|---|---|
| `c + o` | 预览 CO/CO₂（默认 CO），成功仅加入 `co` | 玩家选 `co` 或 `co2`；AI 选 ID 排序首项 | CO₂ 定义和选择 UI 是切片新增。 |
| `n + o` | 预览 NO/NO₂（默认 NO₂），成功仅加入 `no2` | 玩家选 `no` 或 `no2`；AI 选 ID 排序首项 | NO 定义和选择 UI 是切片新增。 |

#### 配方数据建议

将配方配置为显式数据：规范化输入对、输入类型、候选产物 ID 列表、反应基础费/费用修正接口、配方来源、状态标签。切片数据至少含 MT-05 六组；载入时验证键唯一、输入确属元素牌、候选产品非空且都能解析。仅存在预览文字不能证明配方有效。

#### 反应结算顺序（单场切片）

1. 验证战斗进行中、调用者为当前行动方、两个槽各有一张本方手牌元素卡实例，实例 ID 不同，且候选配方存在。
2. 若产物多于一个，向玩家显示候选并等待选中；AI 依据 MT-06 选 ID 字典序首项。未选/取消不进入后续步骤。
3. 验证 `energy >= max(0, 2 - C_discount)`。失败返回拒绝并保留全部状态。
4. 原子提交：扣能量，若本次使用 C 折扣则消费该标记；按左槽/右槽顺序将两输入放入弃牌堆，清空槽，追加一个所选产物实例到手牌。
5. 若本方本回合尚未触发首次反应 fixture 抽牌，标记已触发并尝试抽 1；若有 B 卡待抽标记，再消费标记并尝试额外抽 1。每次抽牌都从牌库顶部取出并追加到 hand；空堆不产生实例。
6. 完整提交后按 MT-07 检查胜负并返回事件结果。候选产品、C 折扣和 B 状态均由战斗状态记录，不从 UI 文案推断。

`c + c` 的切片产物 ID 为 `c`，即生成同一 `c` 定义的一张新卡实例；它保留 `c` 的元素牌资格和打出效果。这是复用原型目录的临时抽象，不主张单质碳具有该游戏效果。

### 8. 能量、回合与抽牌

#### 设计已确认部分

- 正式阵容的初始能量等于所选出战角色能量字段之和。
- 出牌需要消耗能量；产品文档没有完整费用表。

#### 原型实际数值

- 每张当前卡费用为 1 或 2；反应基础费 2；C 卡令下一次反应减费 1，折扣最低可降到 0。
- 初始战斗状态固定为 8/8 能量；`EndTurn` 回合 +1、恢复 2、上限 8。
- 回合结束清除首次伤害、首次反应、S 卡下次伤害增益；不清除 C 折扣、B 待抽标记或已放入反应槽的牌。
- 抽牌来源是 Unity 随机池，允许重复；首次成功反应固定抽 1（日志标为 C passive），B 效果可另抽 1，Ar 立即抽 1。

#### 单场切片迁移期规则（MT-02/03/04）

- 开场双方 HP 30、能量 8/8、手牌各 10 张；玩家先行。HP 与能量均为 fixture 常数，不来自角色面板。
- 玩家可以进行多个合法动作后主动结束；无合法动作时也可结束。AI 回合最多执行一项 MT-06 规则选出的动作，随后自动结束。
- 双方第一次行动均不额外抽牌。之后每次进入己方回合时先 `energy = min(8, energy + 2)`，再尝试抽 1 张；抽牌堆空时无效果。
- C 卡的反应折扣只供本方下一次成功反应使用；本方结束回合未用则清除。B 卡的待抽标记跨回合保留到下一次成功反应；当抽牌堆为空仍消费标记但不抽牌。
- S 卡 `+1` 用于本方下一次成功伤害动作，结束回合未用即移除。N 卡 `-1` 减免下一次非负来袭伤害中的 1 点；若未触发，在对手下一次回合结束时移除，即使对手该回合没有合法动作。
- Ar 牌打出后立刻尝试抽 1；牌库空时仍扣费、进弃牌，抽牌无效果。
- 结束回合清除本回合一次性伤害/反应标志和未用 C/S 效果；未结算的槽牌退回手牌。B 待抽按上文跨回合保留。

#### 回合状态机（单场切片）

| 顺序 | 阶段与规则 |
|---|---|
| 1 | 初始化 `round=1`，双方 `side_turn_count=0`；设置双方 30 HP、8/8 能量、10 张起手、12 张抽牌堆。玩家 `BeginTurn` 后进入玩家行动。 |
| 2 | 每次 `BeginTurn(side)`：若该方 `side_turn_count > 0`，先恢复 `min(8, energy + 2)` 再尝试抽 1；然后重置该方首伤/首反应标记并将 `side_turn_count += 1`。双方第一次行动跳过恢复/抽牌。 |
| 3 | 玩家行动：允许合法出牌/反应；玩家手动 End Turn，或在无合法动作时自动 End Turn。若有未完成槽牌则按原 hand index 退回；清除本方到期的 C/S 效果。 |
| 4 | AI `BeginTurn` 后按 MT-06 执行至多一项合法动作；没有合法动作则跳过。然后结束 AI 回合，清理其到期 C/S 并处理对手回合结束时的 N 效果到期。 |
| 5 | `round += 1`，再次调用玩家 `BeginTurn`。每次玩家或 AI 原子动作结束后结算终局；若仍 ongoing，当前行动方可以继续（玩家）或结束该阶段（AI）。 |

N 减伤标记在持有方的对手下一回合结束时到期；即使对手没有合法动作并跳过，也照常移除。首伤/首反应标记每次 BeginTurn 重置，C/S 效果在持有方 EndTurn 移除，B 待抽标记跨回合保留。

### 9. 胜利、失败和终局

**设计已确认（条件清单）**：产品文档将敌方 HP 到 0 与敌方失去所有手牌都列为胜利条件，但没有说明两者是 OR 还是 AND，也没有玩家失败、平局或检查时机规则。

**原型实际行为**：HP 伤害最低封顶为 0；没有 outcome 状态或终局检查；敌方手牌数字固定为 10，没有对手牌区；玩家 HP 为 0 也不触发失败。

**MIGRATION-TEMP (autonomous), MT-07**：任一战斗方满足 `HP <= 0` 或 `hand.size == 0` 即失败（OR 解释）。另一方获胜；一个原子动作的完整效果全部结算后再检查。如果同一动作后双方都满足失败条件，结果为 `draw`。因此造成对手 HP 归零但自身同步空手的效果会导致平局；胜负不会因为检查顺序偏向一方。手牌定义为当前 hand 区域数量，不包含抽牌堆或弃牌堆。反应产生的产物和所有动作触发的抽牌先加入手牌，再检查空手。回合结束不额外触发胜负检查，因本规则只在动作结算后及初始化时检查。初始化双方均非空且存活，故开局为 `ongoing`。

结果枚举固定为 `ongoing / player_won / player_lost / draw`。终局进入后拒绝出牌、放槽、清槽、Resolve、AI 动作和回合推进；只允许检查卡牌、查看日志和重开。此规则能让 HP 路线与空手路线分别测试，需在后续正式规则审查时重新确认 OR 语义。

### 10. 单场 2D 战斗切片

#### 交付目标

提供一个 PC 可启动的完整单场战斗体验，证明 Unity 规则、卡牌素材和 UI 交互能在 Godot 形成可玩闭环。该切片不是冒险系统、角色 roster 页面或最终内容平衡版。

#### 交付内容边界

1. 一张 Godot 2D 战斗主场景，有玩家信息区、对手信息区、手牌区、两张反应牌槽、配方预览/选择、目标区域、结束回合、清槽、卡牌检查、动作日志和胜负结果。
2. 一个本地玩家侧和一个对手侧；一个预先配置的双方 fixture；一套 MT-05 暂定且可解析、可产生实际产物的配方数据。
3. 出牌、反应放置、预览、确认/失败、费用、伤害、抽牌、回合推进和结果展示都有状态反馈。
4. 至少一条玩家胜利和一条玩家失败路径可以重复验证；自动化规则测试分别覆盖 HP、空手及双方同时失败的临时规则分支。
5. 可重开同一场战斗；本切片不要求跨局保存或解锁。
6. 关键流程可用键盘/鼠标操作；手柄只做部分支持，不作为通过条件；没有触控 UI。
7. 在目标机器上对 60 FPS / 16.6 ms、最多 1,000 个 2D draw calls、2 GB 运行内存预算留存测量证据；这些是暂定预算，超出时记录实测和影响，不能用静态估算声称通过。

#### 完整夹具规则（MIGRATION-TEMP autonomous）

下面的规则合在一起定义交付用的一整场战斗，实作时不得由不同场景各自另选数值：

| 属性 | 玩家 | AI 对手 |
|---|---|---|
| 起始 HP | 30/30 | 30/30 |
| 起始能量 | 8/8 | 8/8 |
| 固定起手 | `c,n,o,cl,b,s,ar,co,no2,h2o2` | 同一组 ID，各自独立卡实例 |
| 有限抽牌堆 | `c,n,o,cl,b,f,s,ar,co,no2,h2o2,cl2`，每个定义 1 张 | 同一组 ID，独立牌区 |
| 抽牌顺序 | 使用 fixture seed `0x54434101` 洗牌，并记录实际顺序 | 用同一 seed 独立洗牌，保证两方相同序列 |
| 回合/动作 | 玩家先行，可执行多个合法动作后主动结束；无合法动作时自动结束 | 每个己方回合最多执行一项合法动作，随后自动结束 |
| 每回合起始 | 第一次开场不抽牌；以后先恢复 2（上限 8）再抽 1 | 与玩家相同 |

起手 10 张与 12 张有限抽牌堆是两个独立列表，所以总计每方 22 个起始卡实例，定义 ID 可重复但实例 ID 必须唯一。抽牌堆空后不洗弃牌；生成的产品实例可以令总实例数增加。牌被使用后放弃牌堆；弃牌牌不会返回手牌或牌库。

**AI 选择算法**：只在 AI 的首次/后续行动阶段调用一次；不能以多步连锁行动绕过每回合一动作上限。先把 hand 中所有两卡组合按 `(card_definition_id, instance_id)` 排序，找出配方有效且支付得起的组合；按规范化定义 ID 对排序取第一组，多个产物时按产物 ID 字典序取第一项。若无可用反应，筛选当前能支付且目标合法的伤害牌，按基础伤害从高到低、定义 ID、实例 ID 顺序选第一张。仍无伤害牌时，在费用可支付、目标合法的自用牌中按费用从低到高、定义 ID、实例 ID 选第一张。没有候选时不行动并结束回合。AI 的出牌/反应使用与玩家相同规则和效果结算；如果动作被校验拒绝，记录原因并直接结束回合，不再尝试下一候选，防止无限重试。

玩家可选敌方目标的伤害牌，或用自用牌/反应。AI 也遵循目标合法性。双方均可通过 HP=0 或手牌清空输掉；测试工具可用预置 fixture 状态覆盖起手，以快速验证四条终局分支，但默认游戏入口必须使用上表配置。测试预置状态不可修改战斗规则本身。

**效果所有权**：fixture 不创建 C/N/O/Cl 角色实例，因此不运行角色被动。为对照 Unity 旧行为，在每一方的战斗修正列表显式启用两项 `prototype_fixture` 效果：本方每个己方回合的首个伤害动作 +1；本方每回合首次成功反应后抽 1。它们不显示为“C/O 被动”，不读取角色数据，未来可在角色系统投入后单独移除。C/B/S/N/Ar 则是卡牌效果，按 MT-04 的生命周期运行。

#### UI 与输入

现有 Unity UI 由横向战斗布局、牌区、反应区、双方信息、预览、日志和 End Turn/Clear/Resolve 按钮组成；[TCA_UI_Guide.md](../../TCA_UI_Guide.md) 和 [TCA_UI_Authoring_Checklist.md](../../TCA_UI_Authoring_Checklist.md) 描述的是 Unity Canvas/Prefab/TMP 的制作流程，只能提供功能清单，不是 Godot 实现规范。

| 输入 | 切片要求 | 状态 |
|---|---|---|
| 鼠标 | 点击检查牌；拖牌到合法目标/槽位；点击 Resolve、Clear、End Turn、菜单确认/取消和重开。非法目标给出拒绝原因。 | 重建 Unity 输入语义，不要求复制 Prefab。 |
| 键盘 | `Tab/Shift+Tab` 在主要交互控件间移动焦点；方向键在手牌、目标或产物选项中移动；`Enter/Space` 选中/确认焦点控件；`R` 结算有效反应；`C` 清空反应槽；`E` 结束回合；`Escape` 取消当前选择/关闭产物选择或结果前确认框。焦点状态清楚可见。 | 具体绑定为 MT-10 暂定默认。关键操作不依赖鼠标拖放唯一入口；可在一个流程中混用键鼠。 |
| 手柄 | 可部分导航和操作，不作为关键规则路径唯一输入。 | 用户已确认部分支持；映射待定。 |
| 触控 | 不实现。 | 用户已确认不支持。 |

各关键操作都必须可由键盘/鼠标操作路径触达；鼠标拖放不能是放牌、选目标或放入反应槽的唯一入口。玩家可在同一流程中混用键盘和鼠标。不要求纯键盘完成整场，也不要求每条命令分别提供键盘和鼠标两套入口。键盘焦点应清楚可见；手牌可通过焦点选择后再选择槽位/目标，主要按钮可通过焦点激活。

## Formulas

本节将产品规则和原型公式分开。产品只确认初始能量求和和角色牌数；下表的原型公式可用于兼容验证，不代表已锁定平衡。

| 公式/量 | 定义 | 来源/状态 | 变量/边界 |
|---|---|---|---|
| 每角色牌数 | `4 自身元素 + 2 左邻 + 2 右邻 + 2 招牌 = 10` | 产品文档；设计已确认 | 对每个上阵角色成立；重复条目表示多个牌实例。 |
| 组合条目总数 | `deck_entry_count = Σ character_deck_entries = 10 × party_size` | 由产品每角色 10 张推导 | `0 ≤ party_size ≤ 4`；是否合并为单一抽牌堆待定。 |
| 初始能量 | `starting_energy = Σ active_character.energy` | 产品文档；设计已确认 | 每个选中角色的 `energy` 必须有定义；上限是否等于总和待定。 |
| 起始 fixture 卡数 | `opening_hand 10 + draw_pile 12 = 22 instances per side` | MT-02；迁移期暂定 | 两个列表独立；ID 可重复，instance ID 必须不同。 |
| 切片反应费用 | `max(0, 2 - C_discount)` | Unity `ResolveReaction` + MT-04 | 基础费 2；C 卡折扣为 1，只在下一次成功反应消费；失败不消费。 |
| 切片伤害 | `max(0, base_damage + first_damage_bonus + S_bonus - N_reduction)` | Unity 卡牌效果＋MT-04/09 | 每方每己方回合首个伤害动作 +1 fixture；S 下一次伤害 +1；N 下一次伤害抵消 1。 |
| HP 结算 | `target_hp = max(0, target_hp - resolved_damage)` | Unity 实际行为；MT-07 终局补齐 | 动作完整结算后检查 HP 和 hand；HP 不可为负。 |
| 切片回合恢复 | `energy = min(8, current_energy + 2)` | Unity `EndTurn`；MT-03 | 各方自己的第 2 次及之后回合开始执行；第 1 次开局状态已是 8。 |
| 手动抽牌 | `draw_one() = pop_front(draw_pile)`；空堆则 no-op | MT-02/03 | 双方首次行动不抽；之后各己方回合开始抽 1。效果抽牌也使用相同有限牌堆。 |
| 终局条件 | `defeated(side) = (HP <= 0) OR (hand_count == 0)` | 产品条件清单＋MT-07 | 检查在动作效果、生成产物和触发抽牌均结算后；同一原子动作双方同时失败为 draw。 |

若任一数值从原型升级为正式平衡常量，需在内容数据/GDD/测试中只有一个权威来源，并记录决策来源；不能让牌面文案、配置值和测试夹具各自保留不同数字。

## Edge Cases

| 情况 | 所需行为 / 当前状态 | 状态 |
|---|---|---|
| 卡牌不在行动方手牌/实例属于另一方 | 拒绝；费用、区域、效果标记、抽牌与 HP 全部不变。 | Unity 缺少 Remove 返回值校验；切片必须校验实例所有权/区域。 |
| 能量不足 | 拒绝完整动作；槽位可以继续编辑，状态不变。 | Unity 会在扣费前校验；切片保持原子性。 |
| 槽位缺一张或重复添加满槽 | 缺牌不可结算；每槽至多一个实例；同一实例不能占两个槽。 | 规则层拒绝。 |
| 无效配方 | 显示当前切片不支持，槽牌保留，可清除/换牌；不扣能量、不抽牌。 | MT-05/08。 |
| 多产物反应未选/取消 | 保持两个输入在槽中，费用、抽牌、弃牌、产物均不变；取消回到槽位操作。 | MT-08；选择产物的产品需求已确认。 |
| 同元素配方无产物 | 数据校验拒绝该配方；MT-05 的三种同元素配方都配置可解析产物。 | 修复 Unity 当前 C+C/N+N/O+O 的无产物成功缺陷。 |
| 同定义多实例 | 通过 instance ID 区分；打出/反应只移动所选实例。 | 必须满足牌区唯一所有权不变量。 |
| 回合结束时反应槽有牌 | 依槽位原始 hand index 顺序退回手牌；两张输入都不消费。 | MT-08。 |
| C/S 效果跨回合未触发 | 清除；B 待抽跨回合保留直到成功反应；N 减伤到对手下一次动作结束过期。 | MT-04 明确的切片持续时间。 |
| 抽牌堆耗尽 | 抽牌 no-op；不随机生成、不重洗弃牌；触发抽牌的卡/效果仍按成功动作消耗。 | MT-02/04。 |
| 目标已倒下/战斗已结束 | 拒绝出牌、反应、结束回合和 AI 动作；允许查看日志、重开。 | MT-07；终局只设置一次。 |
| 一次动作同时触发多项规则 | 完整执行卡牌/反应效果、所有该动作即时抽牌与产品生成后再评估终局。 | 终局检查原子性；防止先检查空手再漏掉同动作抽牌。 |
| 双方同一动作后都满足失败 | 返回 draw，不按 UI 调用顺序优先一方。 | MT-07。 |
| 固定种子/随机结果 | seed `0x54434101` 注入独立双方 RNG；每方保存并显示/记录其洗牌序列，以便复现抽牌。 | MT-02；不依赖全局随机状态。 |

## Acceptance Criteria

下面的标准直接按本文单场夹具判定。标记为 `MIGRATION-TEMP (autonomous)` 的内容可实施、可测试并用于外部验收；负责人审阅后可替换。完整 roster 和正式平衡问题不阻塞单场切片验收。

### 规则与数据

1. **Given** 战斗内容加载一副牌，**When** 校验卡牌数据，**Then** 缺少/重复 ID、负费用、伤害字段与效果不匹配、无效产品引用都返回带 ID 和来源的错误，且不能开始战斗。
2. **Given** 一张卡牌实例，**When** 它出牌或进入反应槽，**Then** 实例属于当前行动方且实际位于允许区域；同一实例不能同时处于手牌和反应槽。
3. **Given** 玩家当前能量低于卡牌/反应费用，**When** 提交动作，**Then** 命令失败且 HP、能量、手牌、槽位、效果标记和抽牌状态都保持不变。
4. **Given** 一对 MT-05 单场 fixture 配方，**When** 两个输入按任意槽位顺序放置，**Then** 获得同一候选产品列表；每个产品 ID 均可解析到有效卡牌定义。
5. **Given** 配方候选产品数大于 1，**When** 玩家未选择或取消选择，**Then** 不扣费、不消费输入、不生成产物，槽位保持可编辑。确认后只生成所选的一种物质。**状态：产品选择为设计已确认，取消的原子回退为 MT-08。**
6. **Given** 一对不支持的元素，**When** 尝试结算，**Then** 不扣费、不抽牌、不清空槽位，并提供键鼠可理解的失败反馈。
7. **Given** 同 ID 的多个牌实例，**When** 玩家只用其中一张，**Then** 只有被选择的实例移区或消费。**状态：迁移数据不变量。**

### 战斗状态与胜负

8. **Given** 初始化切片，**When** 开始首轮，**Then** 双方均为 30 HP、8/8 能量和各 10 张固定手牌，玩家先行；牌库各 12 张，实例独立，抽牌由 fixture seed `0x54434101` 决定。
9. **Given** 双方完成初始开场动作，**When** 任一方进入自己的后续回合，**Then** 该方先恢复 2 点能量（上限 8）并抽 1 张；抽牌堆空时抽牌不改变状态。AI 每回合执行至多一个算法选定的合法动作后结束。
10. **Given** HP≤0 或当前手牌为 0，**When** 完整原子动作结算后评估结果，**Then** 该方依 MT-07 失败；对方获胜；双方同时失败判平局；终局后常规命令不能再改状态。空手检查不计弃牌/抽牌堆。
11. **Given** 6 种 MT-05 配方，**When** 分别提交任意输入顺序，**Then** 六种均能生成唯一可解析产物或多产物候选；多产物需确认；未列配方、缺牌、非法目标或能量不足均零状态变更。

### 键鼠 UI 与单场切片

12. **Given** PC 玩家使用确认的键鼠输入，**When** 完成战斗主流程，**Then** 可以检查牌、出牌/选目标、放入两张反应牌、选产物、清槽、结束回合、查看结果和重开；流程可混用键盘与鼠标，拖放不是唯一入口。无需纯键盘完成整场，也不要求每条命令有两种设备入口。
13. **Given** 使用部分支持的手柄，**When** 操作已映射控件，**Then** 已声明的手柄路径可用；关键流程仍可用键盘/鼠标完成。触控控件不出现。
14. **Given** 玩家检查战斗卡牌，**When** HUD 展示详情，**Then** 显示名称、费用、效果和合法目标，不显示 Damage/Buff/Solvent 内部分类名。
15. **Given** 已打包的 PC 构建，**When** 外部测试者从干净解压目录启动，**Then** 可开始默认战斗、完成一个胜负终局、查看结果并重新开战；不需要 Godot Editor、未打包源素材或开发机绝对路径，不依赖冒险/存档服务。
16. **Given** Godot 的目标 PC 构建，**When** 对完整单场切片采集性能证据，**Then** 记录帧时间、2D draw calls、运行内存和测试设备；以 60 FPS/16.6 ms、≤1,000 draw calls、≤2 GB 暂定目标比较，任何超限有可复核记录。不得用未采集数据声称达标。

### gdUnit4 所需不变量

实现后至少为规则逻辑建立如下自动化检查；这不是当前已运行的测试清单：

- 能量从不小于 0，且不大于已定义上限；失败动作零部分写入。
- HP 被伤害后不小于 0；终局状态不可被普通动作改回继续中。
- 每个牌实例在一个且仅一个已建模区域；多份相同定义牌是不同实例。
- 每个反应槽至多一个实例；有效反应消费正好两个输入并生成至多一个已确认产物。
- 配方输入顺序无关；重复/无效配方键在内容校验中被拒绝。
- 每个持续效果精确符合已批准的触发次数和结束时点；回合推进不遗留未定义标记。
- 抽牌测试通过注入固定牌序/随机源实现确定性；事件触发次数不重复、不丢失。
- 规则测试覆盖有效/无效目标、缺手牌卡、重复实例、空/满反应槽、低能量、未选/取消/确认多产品、HP 胜负、空手胜负、平局与终局锁定。
- AI 对相同 BattleState 总是选择同一动作；并列候选按本文排序收敛，AI 回合最多提交一次动作，动作失败后不循环。
- 固定 seed 生成的双方抽牌顺序可复现并记录；空堆抽牌是 no-op；产物、B、Ar 和回合开始抽牌的顺序满足本文定义。
- 键鼠主流程有 UI/集成测试或可复核的人工记录；不把 Editor 打开场景等同于已验证打包战斗。
