# Unity → Godot 迁移计划

**项目：** TCA（横版化学元素拟人卡牌对战）  
**状态：** 规划中  
**目标引擎：** Godot 4.6.2 stable，GDScript  
**目标平台：** PC（Steam / Epic）  
**决策基线：** 键盘与鼠标为主，部分手柄支持，不支持触控；60 FPS / 16.6 ms、最多 1,000 个 2D draw calls、运行内存不超过 2 GB 为暂定预算。

## 1. 迁移目标

把已有 Unity 战斗原型迁移到可持续开发的 Godot 项目，同时保留 Unity 源工程作为迁移期间的行为与素材参照。第一阶段交付一段可从启动进入、能完整操作并结束的战斗纵切片；后续阶段再扩展角色、冒险和有机化学内容。

迁移应做到：

- 以现有可运行规则和数据为移植基准，逐项记录其与设计文档之间的差异，不在移植时悄悄改变玩法。
- 把规则、内容数据、战斗状态和界面输入分开，避免规则依赖 Godot 节点或 Unity 遗留类型。
- 让玩家可用键鼠完成所有关键战斗操作；手柄作为补充操作方式。
- 用 gdUnit4 建立可重复的逻辑与集成验证入口，并把原有三个 NUnit 用例转成 Godot 测试用例，作为后续迁移任务；本次仅配置框架与 runner，不提前声称这些用例已移植或验证。
- 在 Godot 版本、导出模板和目标硬件确定后，使用同一组场景和基准记录核验暂定性能预算。

## 2. 已知工程基线

### 2.1 现有 Unity 原型

- Unity：2022.3.62t7；项目还记录了 Tuanjie Editor 1.8.5。
- 运行时代码位于 `Assets/Scripts/TCA/`，包括卡牌与角色数据、战斗状态、战斗规则、资源提供器、卡牌表现和战斗界面 Presenter/bootstrap。
- 当前有三个 Unity 场景：BattlePrototype、Intro、SampleScene。它们不是 Godot 场景，迁移时应重新搭建 `.tscn`，而不是尝试转换序列化场景文件。
- `Assets/Tests/EditMode/BattlePrototypeRulesTests.cs` 有 3 个 NUnit 用例：伤害牌消耗能量并造成伤害；完成反应生成产物并清空反应槽；清空反应选择后卡牌回到手牌。
- 当前首发目录有 12 张卡、4 个角色；角色表另有 14 个角色概念。原型起手手牌为 10 张。
- 反应表当前支持 C+O→CO、N+O→NO₂、Cl+Cl→Cl₂，以及 C+C、N+N、O+O 的单质反应。C+O 与 N+O 的预览文本列出多个候选，但实际默认只产出 CO 与 NO₂。
- 战斗原型初值为双方 30 HP、8/8 能量、每回合恢复 2 点能量，反应消耗 2 点；角色卡组数据则另有 22–28 HP 与每角色 2 点能量。两组初值的关系需要在后续平衡/设计阶段澄清。
- 已落地的规则效果包括：O 首张伤害牌 +1（目前对所有阵容生效）；C 使下一次反应少花 1 能量；B 在下次成功反应后抽 1 张；S 使下一张伤害牌 +1；Ar 抽 1 张。C 角色首次成功反应后抽 1 张也在规则中，但与角色设定表中的被动不一致。
- N 与 Cl 的卡牌/角色描述有数据记录，但当前 `BattlePrototypeRules` 尚未完整实现其防御或干扰效果。迁移需保留为显式缺口，不能根据描述自行补规则。
- `EndTurn` 会清除 S 增伤和每回合标记，但不会清除未使用的 C 折扣、B 待抽标记或反应槽卡牌；规则方法也没有验证传入的卡确实属于当前手牌。详情见规则对照矩阵。
- `TCA-Godot版.md` 位于仓库外一层，描述战斗、冒险、角色方向；冒险和有机机制尚未完成。迁移期间不移动或重写该文件，后续应把已确认内容纳入正式 GDD。

- 卡牌、美术 UI、战斗背景、引导背景和字体等素材原在 `Assets/Resources/`；41 张旧 PNG 目前只存在于隔离审核副本 `Assets/art/`，不作为 Godot 运行资源。Godot 专用 `godot_assets/` 已加入 4 张原创角色立绘、1 张原创背景、2 张原创 VFX 候选、4 枚 SVG 状态图标和 1 张 SVG 卡框；来源与 SHA-256 见 [资产生成记录](../../production/art/asset-provenance.md)。

- 四个图片目录有 41 张 PNG、共 31,676,125 B（30.21 MiB）；其中 3 组内容完全重复。UI 目录实有 26 张图；缺失清单标题写 25，但它的分项和实际目录都是 26。

- 根目录 Godot 项目已经建立。Unity 的 `Assets/`、`Packages/`、`ProjectSettings/` 和本机 Unity 缓存目录已加 `.gdignore` 隔离。Windows 不区分 `assets/` 与 `Assets/` 大小写，因此 Godot 运行资源根目录使用独立 `godot_assets/`；旧 PNG 副本留在 `Assets/art/` 隔离审核，不进入 Godot 导入或发行包。
- `.gitignore` 已增加 `.godot/` 导入缓存以及 `reports/`、`exports/` 忽略规则；没有修改 Unity 资产或其 `.meta`。

## 3. 目标结构与边界

Godot 项目已放在仓库根目录，以便与 CCGS 项目配置保持一致。新增的 Godot 内容按用途分区：

```text
godot_assets/characters/      # Godot 专用角色立绘
godot_assets/backgrounds/     # Godot 专用背景
godot_assets/ui/              # SVG 卡框、状态图标与界面素材
godot_assets/vfx/             # 反应与命中特效候选
godot_assets/data/cards/      # 卡牌 Resource 定义
godot_assets/data/characters/ # 角色 Resource 定义
godot_assets/data/reactions/  # 反应表或反应 Resource
scenes/                 # .tscn：入口、战斗、可复用 UI
src/domain/             # 纯规则、状态、结果类型与验证
src/application/        # 战斗流程用例、输入命令与界面协调
src/ui/                 # 卡牌、手牌、反应区、HUD 的节点脚本
tests/                  # gdUnit4 测试与共享 fixture
docs/migration/         # 迁移计划与阶段证据
```

分层约定：

1. **Domain：** 使用 GDScript 类型表达卡牌定义、角色定义、战斗状态、动作结果、反应判定与回合规则；不读取节点树、不加载贴图、不直接处理鼠标事件。
2. **Content：** 将静态卡牌、角色与反应内容放入 Godot `Resource`/`.tres`（或经评估后使用 JSON）；通过启动校验发现缺字段、未知卡牌 id、无效目标和缺失素材。
3. **Application：** 接收“出牌、放入反应槽、清空选择、合成、结束回合”等明确意图，调用 Domain，再向界面返回状态变更与可读事件。
4. **Presentation：** `.tscn` 组合界面，脚本只负责显示状态、发出操作意图和播放反馈；卡牌外观不得成为规则数据源。
5. **Assets：** Godot 专用原创 PNG/SVG 已入 `godot_assets/`；逐项核对导入、裁切、卡面排版和特效帧仍在进行。旧 PNG 保留在 `Assets/art/` 隔离区，字体许可未确认；不复用 Unity `.meta`、Prefab、TMP SDF 资产或 Addressables。

全局单例只用于确有跨场景生命周期需要的服务；战斗规则不做 Autoload。输入动作使用 Godot InputMap，按键最终绑定待首个可操作战斗场景确定，并需提供键鼠路径完成所有关键操作。

## 4. 分阶段实施

### 阶段 0：冻结基线与迁移准备

- 保存 Unity 版本、目录清单、关键规则和 3 个现有测试所表达的行为。
- 已完成静态规则与素材/场景盘点，见本计划链接的两份审计文档；测试和游戏运行状态未验证。
- 形成素材授权与字体许可记录；确认 Steam/Epic 首发所需的窗口尺寸、宽高比、语言和导出环境仍待定。
- 不清理 Unity 工程，不迁移旧场景序列化文件，不在本阶段扩写冒险或有机规则。

**进度：** 静态规则与素材审计已提供可追溯基线；旧图仅为审核副本，Godot 专用目录已有原创素材并记录来源与哈希。Unity 导入隔离已确认，原创资源的场景视觉审查和 VFX atlas 验证仍待完成，旧字体许可仍未核实。

**退出条件：** 现有可执行规则和素材都有可追溯清单；未知项有负责人/决策点；Unity 基线仍可恢复。

### 阶段 1：Godot 工程与自动化基础

- 已写入 Godot 4.6.2、GDScript、桌面 2D Forward+ 与 Godot Physics 2D 配置，并建立根目录 `project.godot`。
- 已启用目录隔离：Unity 专属目录不进入 Godot 导入扫描；Unity 工程本身未改动。
- 已加入 gdUnit4 6.2.1 插件、官方命令行 runner 包装入口和测试 README；测试用例尚未移植。
- 已配置 `.godot/` 忽略规则、本地引擎路径和命名规范。导出 preset 尚未确定，构建命令保持待配置。
- 当前交付范围只有框架、插件和 runner；规则测试、CI 工作流与导出任务属于后续故事。

**当前状态：** Godot 4.6.2 无界面编辑器导入检查已通过，工程完成资源扫描并识别 gdUnit4 6.2.1 插件；这不是测试套件结果。测试 runner 尚未实际运行，Godot 玩法测试仍未建立。

**退出条件：** Godot 可识别项目并启动编辑器；gdUnit4 插件可加载；runner 指向官方受支持的命令行工具；没有导入 Unity 缓存或误改 Unity 文件。

### 阶段 2：领域规则与内容数据移植

- 先移植基础模型与 12 张卡、4 个角色、反应表和原型初始状态。
- 把随机抽牌改为可注入随机源或牌堆接口，让规则可确定性复现；明确洗牌、无牌可抽和牌堆耗尽行为前不扩展规则。
- 移植已实现玩法行为：合法目标、能量扣除、伤害、反应放置/清空/结算、反应费用折扣、抽牌、回合恢复与暂存加成。
- 显式登记原实现的不一致：例如 C/N 多产物预览与单一默认产物；角色定义 HP 与战斗原型 HP；N/Cl 描述与规则实现不同；游戏设计中的“手牌耗尽胜利”在战斗规则类中未见结算实现。
- 不在移植时自行决定敌方行动、牌堆循环、抽牌上限、胜利优先级、化合物候选选择 UI 或能量如何从角色队伍计算。

**退出条件：** 规则层在不实例化 UI 场景的条件下可执行；每个已实现行为都有明确用例；所有内容数据通过启动校验；已知差异有记录。

### 阶段 3：战斗纵切片与键鼠交互

- 重新搭建入口与战斗 `.tscn`，不导入 Unity `.scene` 或 Prefab。
- 实现战斗 HUD、手牌、玩家/敌方区域、反应槽、产物预览、能量/血量/回合信息、日志和操作反馈。
- 让鼠标可点击或拖放卡牌，并能清晰取消、退回反应选择；为关键操作提供键盘等价入口，具体按键与焦点顺序随界面原型确认。
- 手柄只覆盖经确认的浏览、焦点移动、确认与返回；不让手柄依赖触摸语义。触控不纳入当前平台范围。
- 迁移现有素材并在目标分辨率下重新检查安全边距、文字可读性、卡牌缩放与不同窗口尺寸。
- 把现有三个 NUnit 行为转成 gdUnit4 领域测试，并补充关键失败路径、回合边界与输入到规则的集成检查；这些是该阶段的实现任务，不属于本次框架配置。

**退出条件：** 玩家可以启动到战斗，使用键鼠完成合法/非法出牌、反应组合、清空反应区、结束回合，并观察到状态反馈；核心规则覆盖有 gdUnit4 证据；无关键操作只能靠拖放或手柄完成。

### 阶段 4：迁移验收与平台准备

- 在锁定的 Windows PC 参考机上测量 60 FPS/16.6 ms 和运行内存；以代表性战斗场景测 draw calls，并说明测量方式、场景、构建类型和硬件。
- 在性能验证前决定是否保留 1,000 draw calls 为硬上限，还是作为预算目标；若 Godot 的统计口径与原暂定口径不同，记录对应指标，避免直接等同。
- 完成固定窗口尺寸、缩放、帧率策略、音频设备、键鼠/手柄接入与存档位置验证。
- Steam/Epic 商店、成就、云存档、输入层、导出 preset 和商店 SDK 单独规划；不能把“PC（Steam/Epic）”视作这些集成已经实现。
- 以功能差异、阻断问题、测试证据、性能测量和可恢复方案作为 Unity 切换决策材料。

**退出条件：** 功能验收与质量证据通过；所有 P0/P1 差异关闭或获明确延期；可复现导出；Unity 项目仍留有可恢复快照；项目负责人确认后才进入 Unity 停止维护/清理阶段。

## 6. gdUnit4 配置约定

- 使用 gdUnit4 **v6.2.1**；已核对发行 tag 与插件 `plugin.cfg`。Godot 4.6.2 的无界面编辑器导入已识别插件，但尚未运行 gdUnit4 测试命令或测试套件。
- 插件按官方目录结构放在 `addons/gdUnit4/`，启用入口登记在 Godot 项目配置中。
- runner 应调用官方 `addons/gdUnit4/bin/GdUnitCmdTool.gd`；不要使用过期示例里的 `addons/gdUnit4/GdUnitRunner.gd`。
- 将测试入口统一为 `godot --headless --script tests/gdunit4_runner.gd` 或一层薄包装，且包装需把参数/退出码传给官方命令行工具。最终以实际插件版本文档为准。
- 测试目录按 `tests/unit/domain/`、`tests/integration/`、`tests/fixtures/` 划分；runner 和 README 已存在，目录中的 Godot 测试用例、完整测试结果与 CI 工作流尚待建立。
- 后续测试最少覆盖现有三个 NUnit 场景、无效动作不改状态、反应结果/费用、每回合重置效果、抽牌注入和内容校验。

**参考：** [gdUnit4 官方 6.2.1 发行版](https://github.com/godot-gdunit-labs/gdUnit4/releases/tag/v6.2.1)、[gdUnit4 官方命令行工具说明](https://godot-gdunit-labs.github.io/gdUnit4/latest/advanced_testing/cmd/)。配置时应再次核对 tag 内的插件版本和命令行入口。

## 7. 风险、待决策项与控制

| 风险/未知项 | 影响 | 处理方式 |
|---|---|---|
| GDD、卡牌文案、Unity 规则代码之间存在差异 | 移植者可能把当前规则与期望规则混为一谈 | 先建立差异表；保持现有可观察行为，未决规则不实现 |
| Unity 与 Godot 文件同处一个仓库 | Godot 可能扫描 Unity 缓存或把 C# 当作游戏源 | 用 Godot 忽略标记隔离 Unity 目录；Godot 可复用资源使用独立目录；Unity 文件保持原样 |
| UI 清单与实际 PNG 数量不同 | 漏图、重复导入或资产映射错误 | 迁移前做完整文件名/尺寸/hash 清单，和文档逐项对账 |
| 反应存在多个化学产物候选 | 玩家选择、平衡和卡牌产物都未明确 | 当前复刻默认产物并保留预览标记；候选选择另立设计决策 |
| 角色级 HP/能量与战斗原型初值不同 | 数据结构迁移可能固化错误来源 | 原样保留两套基线，明确选择战斗配置/角色编队规则后再统一 |
| 性能预算缺少硬件、分辨率和统计定义 | 测量不可复现，draw call 数不可比 | 阶段 4 前锁定参考机、构建方式、场景和统计方法 |
| Steam/Epic 发布目标较宽泛 | 导出、SDK、云存档和成就不明 | 首个可玩切片先做 Windows 本地构建；平台集成作为独立计划 |
| 外层 `TCA-Godot版.md` 尚未纳入仓库 GDD | 设计来源易散失 | 先保留原文件，确认内容后再迁入正式 GDD，不重复维护两份权威稿 |

迁移期间遇到以下问题必须形成明确设计决定，而不能由代码迁移自行推断：

1. “手牌耗尽”胜利条件如何判断，是否是玩家手牌、敌方手牌还是任一方。
2. 出战角色数量和角色属性如何影响初始生命、能量与卡组；与原型固定 30/8 的优先级。
3. 多个反应产物候选如何选择；无产物单质反应的实际效果。
4. N 与 Cl 的保护/干扰被动何时触发、是否能取消效果、如何与回合规则交互。
5. 牌堆组成、抽空后的行为、重复卡身份和战斗结束后的流程。
6. 冒险模式范围及有机机制何时进入本项目阶段。

## 8. 回退与切换策略

- 在 Godot 纵切片达到阶段 3 验收前，Unity 工程仍是现有可运行参照；迁移操作只新增 Godot 文件或复制素材，不删除/搬移 Unity 内容。
- Godot 代码与资源按 Godot 目录管理；不能把 Godot 导入缓存、导出构建和编辑器本地状态提交为源资产。
- 若迁移遇到阻断问题，可暂停 Godot 迁移并从原 Unity 目录继续验证已实现行为；迁移特有修正应留在 Godot 分支/目录，不反向修改 Unity 来掩盖差异。
- Unity 停止维护、旧资源删除或仓库拆分是单独切换决策，需在 Godot 纵切片证据齐备后再执行。
